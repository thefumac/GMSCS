# 9월 18일 인증유지 고객 문제 수정작업 이력과 과제

---

## 1. 개요 및 작업 배경

- **작업 목적**:
  - GMSCS 경영시스템 전반에서 발생하던 화면별 수치 불일치(고객관리/문서관리 573개사 무조건 고정 출력, 금월 심사 대상 382건 폭증 현상 등)를 해소하고, 런타임에 임의로 생성되던 가상 데이터(Modulo 연산, 샘플 객체 등)를 원천 제거.
  - ISO/IEC 17021 인정 기준에 부합하는 정규 '인증유지 자격' 검증 요건을 수립하여 투명하고 신뢰성 높은 심사·인증 데이터 파이프라인 정립.

## 2. 오늘 시도된 작업 및 주요 성과

### ① `checkAuditDueThreshold` 당월 판정 부등호 교정 (`auditStateUtils.ts`)
- **기존 결함**: 과거 누적 기한초과 건까지 전부 당월 심사로 합산하던 `>=` 부등호 로직으로 인해 '금월 심사 대상' 수치가 382건으로 비정상 폭증.
- **조치 결과**: 당월 동등 비교(`===`)로 판정식을 엄격히 분리하고 기한초과(`isOverdue`)를 독립 연산함으로써, 심사관리의 '금월 심사 대상' 수치를 현실적인 수준(36건)으로 정상화 완료.

### ② 가상 날짜 Modulo(%) 연산 및 날조 코드 완전 폐기 (`CompanyAuditorManager.tsx`)
- **기존 결함**: 런타임에 `index % 4`, `index % months.length` 등으로 심사 유형(1차 사후/2차 사후/갱신/최초)과 차기 도래일을 임의로 날조하던 코드 존재.
- **조치 결과**: Modulo 연산을 전면 폐기하고, 기업 객체에 바인딩된 실제 도래일(`surveillanceDueDate`) 및 ISO 3년 주기 룰을 직접 읽도록 구조 개편.

### ③ 인증심의관리 유령 데이터 및 가상 안건 격리/초기화 (`CertificationManagement.tsx` / `CommitteeManager.tsx`)
- **기존 결함**:
  - `CertificationManagement.tsx`: 프로젝트 목록(1,029건) 전체를 사무국 검토 완료 여부와 무관하게 `GMS-DELIB-...` 심의 안건으로 자동 둔갑시키고, 상단 state에 샘플 기업 3건((주)성우정밀, 한빛테크, 세진케미칼)이 하드코딩되어 상시 노출됨.
- **조치 결과**:
  - 하드코딩된 샘플 데이터 3건을 빈 객체(`{}`)로 완전 초기화.
  - 심사 프로젝트 목록(`projects`) 중 실제로 사무국 검토가 완료되어 **`status === '심의대기'` 또는 `committeeStatus === '심의대기'`로 정식 상정된 건만 필터링**하여 표시하도록 원천 차단.
  - 현재 정식 상정 건이 없으므로 **"현재 상정된 심의 안건이 없습니다 (0건)"**으로 정확히 비워둠.

### ④ 전체 코드 무결성 검증 및 전역 동기화
- `npx tsc --noEmit` 전체 타입 검사 통과 (오류 0건).
- `Remark/all_code.txt` 73개 파일 마스터 번들 최신화 완료.

## 3. 미해결 원인 및 데이터 구조적 한계 분석 (핵심 결론)

### ① 배제식(Negative) 필터링의 무력화 및 Firestore 원본 데이터 한계
- 프론트엔드에서 `isNormalCompany`를 실무 정규 요건 검증식으로 강화하였으나, 현재 Firestore `companies` 컬렉션의 573개 문서가 일괄 `auditState: "일정·계획"` 형태로 마이그레이션되어 있어 데이터베이스 레벨에서 실효/정지 사유 키워드('취소', '정지', '철회' 등)가 전무함.
- 브라우저 콘솔 디버깅 결과(`[DEBUG ClientManagement]`):
  - `total: 573`
  - `normalCount: 573`
  - `inactiveCount: 0`
- 즉, **원본 DB에 상태값 구분이 기록되어 있지 않아** 정상적인 자격 검증식을 적용해도 전체 573건이 그대로 '정상'으로 판정되는 구조적 원인 확인.

### ② 필수 실무 판정 필드의 부재
- ISO 공인 인증기관 실무 기준에 따른 인증 유효성을 정밀 판정하기 위해서는 아래 3대 핵심 필드가 기업별/규격별로 독립 저장되어 있어야 하나, 현재 Firestore 문서 내에 누락되어 있음:
  1. **[규격별 인증서 유효기간 (3년 만료일)]**
  2. **[규격별 최종 심사일자 (Last Audit Date)]**
  3. **[법정 사후관리 만료일 (Surveillance Due Date)]**

### ③ 무리한 프론트엔드 코드 보정의 한계 확인
- 원본 데이터베이스의 스키마와 데이터 값이 미비한 상태에서 프론트엔드 코드(문자열 정규화, 텍스트 비교, 정규식 휴리스틱, 임시 조인 등)만으로 억지 필터링을 시도하는 것은 또 다른 왜곡과 가상 로직을 낳는 악순환임을 최종 확인.

## 4. 향후 해결 과제 (Next Steps)

```mermaid
flowchart LR
    A["[1단계] 인증원 공식 마스터 장부 확보 (엑셀/CSV)"] --> B["[2단계] Firestore companies 배치 마이그레이션"]
    B --> C["[3단계] 프론트엔드 코드 단순화 및 아키텍처 완결"]
```

### [1단계] 인증원 공식 마스터 리스트 확보
- 인증원 공식 관리 장부(엑셀/CSV)를 수령하여 기업별 정규 필드 전수 확보:
  - `사업자등록번호(bizNumber)`
  - `보유 규격(standards: ISO 9001, 14001, 45001 등)`
  - `인증번호(certNo)`
  - `최초인증일(initialCertDate)`
  - `최근심사일(lastAuditDate)`
  - `유효만료일(expiryDate)`
  - `실제 관리상태(status: 정상유지 / 자격정지 / 인증취소 / 자진취소 / 만료)`

### [2단계] Firestore 기업 DB 정규 마이그레이션 (Batch Update) 실행
- 확보된 마스터 리스트를 기준으로 Firestore `companies` 컬렉션을 1회성 스크립트로 전면 갱신(Batch Update)하여 데이터베이스 레벨의 무결성 확보.
- 정상 인증 유지 기업(~300여 개사)과 취소·정지 기업(~200여 개사)을 DB 필드 레벨에서 명확히 구분.

### [3단계] 코드 단순화 및 최종 완결
- 원본 DB가 정규화되면 프론트엔드에 임시로 덧대어졌던 복잡한 땜질식 유틸리티 및 추론 로직을 전면 제거.
- 순수 DB 쿼리 및 단순 상태 바인딩(`c.status === '인증유지'`)만으로 작동하는 깨끗하고 견고한 프로덕션 아키텍처로 최종 확정.
